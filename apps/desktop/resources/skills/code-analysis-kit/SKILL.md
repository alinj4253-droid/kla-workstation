# 代码分析（Code Analysis）

把"读代码、审代码、评估改动"统一成一套可复用的四层工作流，产出结构一致、证据可追溯的分析报告与测试建议。

## 用途

对本地代码项目执行结构化分析，解决两类问题：

- **能力 A｜完整项目代码分析**：输入项目路径，产出项目结构、关键逻辑、模块依赖、潜在风险与现有测试资料，并给出建议测试清单。
- **能力 B｜代码变更影响分析**：基于 Git 差异或可比较的代码版本，追踪修改影响，识别受影响模块、潜在回归风险与需要补充的测试场景。

## 输入源

本技能的输入源是**本地文件夹的项目路径**（local folder path）。所有能力与脚本都以该路径为入口，不做远程仓库拉取、不做在线代码平台抓取。

- **路径形式**：绝对路径优先（如 `D:\workspace\my-app`、`/home/user/my-app`）；相对路径按当前工作目录补全为绝对路径。路径含中文或空格时直接使用原路径，传给脚本时用引号包裹。
- **前置校验**：路径必须存在且为目录。若用户给的是单个文件，取其所在目录或请用户确认项目根目录；若给的是压缩包，先解压再分析；若给的是远程地址，请用户提供已拉到本地的目录路径。
- **多路径输入**：逐个项目独立分析，报告按项目分节呈现，不混合统计。
- **与 Git 的关系**：能力 A 不要求 Git；能力 B 优先使用仓库内的 Git 历史，无 Git 时用 `--compare` 比较两份本地快照目录。

## 何时使用

- 用户要求"分析 / 梳理 / 审查这个项目或代码库"。
- 用户要求评估某次提交、某个分支、某段改动的影响面或回归风险。
- 用户要确定"该测什么 / 漏了什么测试"。
- 用户要求统一多方（多人 / 多智能体）代码分析产出的格式与判定标准。

不适用：单纯询问某段代码的语法或某个 API 的用法（直接回答即可）；非代码的纯文档项目。

## 四层工作流

任何一次分析都按以下四层推进，每层只做本层的事，产出作为下一层的输入。

| 层 | 名称 | 目标 | 加载 |
|---|---|---|---|
| L1 | 任务识别 | 判定任务类型与范围，明确输入、边界与约束 | `references/layer1-task-identification.md` |
| L2 | 项目理解 | 读取项目、识别技术栈、梳理目录结构与模块关系 | `references/layer2-project-understanding.md` |
| L3 | 分析方法 | 执行逻辑检查、变更追踪、风险识别、测试范围判断 | `references/layer3-analysis-methods.md` |
| L4 | 结果规范 | 统一问题分类、证据要求、风险评级、测试建议与报告结构 | `references/layer4-result-spec.md` |

执行顺序固定为 L1 → L2 → L3 → L4。L2 与 L3 之间可反复迭代：L3 发现疑点时回到 L2 按需深读相关代码。

L1 只需判定任务类型与范围（完整项目 / 变更影响 / 指定模块·文件·功能）；完整的方法论细节在需要时再加载对应 reference，不必一开始全部读入。

## 能力路由

在 L1 判定能力类型，再加载对应工作流文件：

- 完整项目分析 → `references/capability-a-full-project.md`
- 变更影响分析 → `references/capability-b-change-impact.md`
- 两者都要 → 先跑能力 A 建立基线，再跑能力 B 做变更定位，共用同一套 L4 规范。

## 辅助脚本

`scripts/` 下两个脚本负责确定性的机械性数据采集，替代重复的目录遍历与 Git 查询。脚本只读、不修改被分析的项目，全部仅用 Python 标准库。

```bash
# 能力 A：扫描项目结构、技术栈、测试资料、入口文件与依赖清单
python scripts/scan_project.py <项目路径> --json

# 能力 B：分析 Git 变更影响面（变更文件、按模块聚合、反向依赖候选）
python scripts/git_impact.py <项目路径> --range <git范围> --json
```

- 加 `--json` 输出机器可读结果供后续推理；省略则输出 Markdown 摘要，可直接放进报告。
- 脚本输出是"原料"，风险判断与结论仍由 L3 的方法执行，不要直接把脚本输出当作最终结论。

## 关键约束

- **证据优先**：每个问题都必须给出可定位的证据（文件路径 + 行号 + 代码片段或命令输出）。无法定位的只记为"待确认"，不得写成结论。
- **不臆测**：读不到的文件、跑不了的命令、缺失的依赖，如实标注为"未覆盖 / 不确定"，不要用推测填充。
- **范围收敛**：只分析 L1 确定的范围；发现范围外的重大风险时单独列出并说明，不擅自扩大分析。
- **结论可复现**：报告中的每一条判定都能由给定证据或命令重新得到。

## 输出

- 报告遵循 L4 结果规范，使用 `assets/report-template.md` 的结构。
- 默认在对话中给出报告；用户要求落盘时写入 Markdown 文件。
- 报告必须包含：分析范围、技术栈与结构结论、问题清单（含证据与风险等级）、测试建议、未覆盖与不确定项。
