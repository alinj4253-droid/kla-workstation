# L3｜分析方法

目标：在项目地图之上，对代码做实质判断——逻辑对不对、改动影响哪些地方、风险在哪里、该测什么。

## 1. 代码逻辑检查

按以下维度检查，逐项对照实际代码找证据，不做泛泛而谈：

- **正确性**：分支是否覆盖全部情况；边界（空值、0、负数、超长、越界）是否处理；类型转换与精度是否安全。
- **错误处理**：异常是否被吞掉（空 catch / 只打日志不处理）；错误是否向上传递或转成合适的结果；失败路径是否回滚。
- **状态与副作用**：共享可变状态、全局变量、隐式副作用；状态机是否存在未定义转移；生命周期是否闭合（打开必关闭、加锁必释放）。
- **幂等与重复**：重复提交 / 重试 / 并发执行下的行为。
- **资源与性能**：循环内的重复 IO / N+1 查询、未加索引的查询、无界缓存或列表增长、大对象常驻。
- **并发**：竞态、死锁风险、锁粒度、异步中的顺序假设、事务边界。
- **安全**：注入（SQL / 命令 / 模板）、越权、缺失鉴权、敏感信息硬编码或泄漏到日志、不安全的反序列化、路径穿越、依赖已知漏洞。
- **可维护性**：重复代码、过长函数、过深嵌套、命名与职责不符、魔法值、注释与实现不一致、被注释掉的死代码。
- **一致性**：同一类问题在不同模块的处理方式是否统一（如错误返回、日志格式、命名约定）。

## 2. 变更追踪（T2 及 T3 中的版本对比）

1. 运行 `scripts/git_impact.py <项目路径> --range <范围> --json`，得到：
   - 变更文件清单（新增 / 修改 / 删除 / 重命名）与增删行数。
   - 变更按模块 / 目录聚合。
   - 反向依赖候选（引用了被改文件的其他文件）。
2. 对每个变更文件读实际 diff，判断改动的**性质和意图**：
   - 是修复、新功能、重构、配置、还是清理？
   - 逻辑被改动了，还是仅格式 / 命名 / 注释？
   - 是否改变了对外接口、数据形状、时序假设、默认值？
3. **影响传播**：从变更点向外扩散——
   - 直接调用方（反向依赖）是否受接口 / 行为变化影响。
   - 共享该数据结构或全局状态的其他模块。
   - 被改动的公共模块 / 高扇入模块，命中面要显式放大。
   - 配置、Schema、迁移、序列化格式变化会波及的运行时与持久化数据。
4. **未变更但相关的**：找出"本该一起改却没改"的地方（调用方未同步、测试未更新、文档 / 类型未更新、迁移缺失）。

## 3. 风险识别

对每个疑点按 L4 的风险维度归类，并判定等级。重点关注：

- 破坏向后兼容的接口 / 数据变更。
- 变更落在高扇入模块或核心调用链上。
- 缺少对应测试保护的核心逻辑。
- 错误处理、边界、并发、安全类缺陷。
- 与变更意图不符或明显漏改的地方。

风险必须落到"哪段代码 + 什么条件下出问题 + 后果"，不能只写"可能有问题"。

## 4. 测试范围判断

测试建议从三处推导，合并去重：

1. **变更直接覆盖**：每个变更文件对应的单元测试是否已存在、是否需更新。
2. **影响传播覆盖**：受影响模块 / 调用方 / 共享数据结构的回归测试。
3. **风险驱动补充**：针对 L3 第 3 节识别出的风险点，设计边界、异常、并发、安全用例。

每条测试建议给出：
- 测试目标（要验证什么行为）。
- 测试层级（单元 / 集成 / E2E）。
- 触发条件与预期结果。
- 优先级（对应 L4 风险等级）。
- 是否已存在（复用 / 更新）还是需新增。

同时给出**回归范围**：为覆盖本次变更及其影响，最小需要重跑的既有测试集合。

## 5. 静态分析工具（可选，按语言选用）

有则运行以补充客观证据，无则跳过并说明。工具不可用时以人工检查替代，不要编造工具输出。

| 语言 / 场景 | 可用工具 |
|---|---|
| JS / TS | `eslint`、`tsc --noEmit`、`depcheck`、`npm audit` |
| Python | `ruff`、`flake8`、`mypy`、`bandit`、`pip-audit` |
| Java / Kotlin | `spotbugs`、`checkstyle`、`pmd`、`dependency-check` |
| Go | `go vet`、`staticcheck`、`gosec` |
| Rust | `cargo clippy`、`cargo audit` |
| PHP | `phpstan`、`psalm` |
| C / C++ | `clang-tidy`、`cppcheck` |
| 通用 | `semgrep`、`gitleaks`（密钥泄漏）、`trivy` / `grype`（依赖与镜像） |
| 复杂度 | `lizard`、`radon`（圈复杂度）、`jscpd`（重复代码） |

运行前确认工具已安装；命令报错或不可用时，记录"未能运行 <工具>：<原因>"，不计入结论。

## 6. 证据纪律

- 每条结论都要能指到 `文件:行号` 或一段命令输出。
- 推断与事实分开标注：事实用陈述句，推断标"（推测）"并给出依据。
- 无法验证的内容统一进入"未覆盖 / 不确定"清单。
