# 能力 B｜代码变更影响分析

基于 Git 差异或可比较的代码版本，追踪修改影响，识别受影响模块、潜在回归风险与需要补充的测试场景。

## 流程

### 步骤 1｜任务识别（L1）
- 确认项目路径（本地文件夹，绝对路径优先）与比较基准（仓库内的 Git 范围，或无 Git 时的两份本地快照目录）。
- 采集变更意图（这次改动想做什么），用于判断是否漏改、是否符合预期。
- 输出任务卡。

### 步骤 2｜项目理解（L2）
- 若尚不了解项目，先建立最小项目地图（技术栈、目录分层、入口、高扇入模块）。
- 变更影响分析依赖"模块关系"，因此必须掌握变更文件在整个依赖图中的位置。

### 步骤 3｜变更追踪（L3 第 2 节）
- 运行 `python scripts/git_impact.py <项目路径> --range <范围> --json`。
- 无 Git 时，用两份快照目录做文件级 diff（脚本的 `--compare` 模式，或人工比对）。
- 读每个变更文件的实际 diff，判定改动性质与意图。
- 沿依赖向外扩散，计算影响面；显式放大高扇入模块与核心调用链上的改动。
- 找出"本该一起改却没改"的遗漏点。

### 步骤 4｜风险与测试（L3 第 3–4 节）
- 对每个受影响点判定回归风险与等级。
- 生成测试建议（变更直接覆盖 / 影响传播覆盖 / 风险驱动补充）。
- 给出最小回归测试范围。

### 步骤 5｜结果规范化（L4）
- 按报告结构成文，重点写"变更摘要 → 影响传播 → 遗漏点 → 测试与回归范围"。

## 输出要点

- 影响面必须落到具体文件 / 函数，而不是"可能影响其他模块"。
- 明确区分：**已验证受影响**（有引用证据）与**疑似受影响**（需进一步确认）。
- 遗漏点（漏改的调用方 / 测试 / 配置 / 迁移）往往是最有价值的发现，单列一节。

## 质量自检

- [ ] 变更文件清单完整（含新增 / 删除 / 重命名）。
- [ ] 每条影响判断都有引用或调用证据。
- [ ] 回归范围明确到"需重跑哪些既有测试"。
- [ ] 补测清单与风险等级对应。
- [ ] 无 Git / 工具不可用等情况已说明。
