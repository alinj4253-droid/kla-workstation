# L1｜任务识别

目标：在读取任何代码之前，先把"要做什么、做多大、做到什么程度"定下来，避免范围失控或答非所问。

## 1. 判定任务类型

把用户请求归入以下三类之一（可叠加）：

| 类型 | 判定信号 | 走向 |
|---|---|---|
| T1 完整项目分析 | "分析这个项目 / 代码库""梳理架构""项目里有什么风险" | 能力 A |
| T2 变更影响分析 | 提到 commit / 分支 / diff / PR / "这次改动""刚改了什么" | 能力 B |
| T3 局部专项分析 | 指定模块、目录、文件、类、函数或某个功能点 | 缩小范围后走 A 或 B |

T3 不是独立能力，而是给 A 或 B 加一个范围过滤器：只分析指定对象及其直接相关代码。

## 2. 采集输入

按类型收集以下最小输入。缺失时按"默认假设"处理并明确标注。

**通用**
- **项目路径（唯一项目来源，本地文件夹）**：绝对路径优先；相对路径按当前工作目录补全为绝对路径；含中文或空格时用原路径，调用脚本时加引号。
- **路径校验**：必须存在且为目录。给到文件 → 取其所在目录或请用户确认根目录；给到压缩包 → 先解压；给到远程地址 → 本技能只接受本地已解压目录，请用户提供本地路径。
- 语言 / 技术栈已知信息（若用户已说明，可直接采信并跳过探测确认）。
- 分析深度：概览（结构 + 顶层风险）｜标准（结构 + 关键逻辑 + 风险 + 测试）｜深度（逐模块 + 依赖链 + 数据流）。

**T2 变更影响分析额外需要**
- 比较基准：Git 范围（如 `HEAD~1`、`main..feature`、某 commit SHA、未提交工作区）或两份可比较的代码版本目录。
- 若无 Git：两份代码快照路径。
- 变更意图（可选但高价值）：这次改动"想做什么"，用于判断是否符合预期、是否有遗漏。

## 3. 界定范围

- 明确包含与排除：如"排除 node_modules / 生成代码 / 第三方依赖 / 测试夹具"。
- 默认忽略目录（除用户特别要求）：`.git`、`node_modules`、`vendor`、`dist`、`build`、`out`、`target`、`__pycache__`、`.venv`、`venv`、`.next`、`.nuxt`、`coverage`、`.idea`、`.vscode`。
- 指定功能点分析时，先定位其入口文件与调用链（见 L2 第 4 节）。

## 4. 澄清策略

只有在下列情况才向用户提问，其余一律按合理默认推进：
- 任务类型无法判断（既可能是 A 也可能是 B）。
- 缺少项目路径或比较基准，且无法从上下文推断。
- 范围边界会导致重大结论差异（如"是否包含测试代码"会改变风险结论）。

提问时一次性给出选项，不要连续追问。默认假设参考：

| 缺失项 | 默认假设 |
|---|---|
| 分析深度 | 标准 |
| Git 范围 | 已暂存 + 未暂存的工作区改动；无改动则回退到最近一次提交 |
| 是否含测试 | 含（测试是风险判断的重要依据） |
| 输出形式 | 对话内 Markdown 报告 |

## 5. 产出：任务卡

在进入 L2 前，用一小段结构化文字固定以下内容（可写给用户确认，也可内部记录）：

```
任务类型：T1 / T2 / T3（叠加）
项目路径：
分析范围：包含 … / 排除 …
分析深度：概览 / 标准 / 深度
比较基准：（T2 必填）
已知约束与假设：
预期产出：报告 + 测试建议清单
```

任务卡一旦确定，L2–L4 均以其为准。
