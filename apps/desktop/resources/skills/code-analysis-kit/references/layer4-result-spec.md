# L4｜结果规范

目标：无论分析者是哪个智能体、跑第几遍，产出的问题分类、证据、评级、测试建议和报告结构都一致、可对比、可复查。

## 1. 统一问题分类

每个问题分配一个类别码，归入唯一主类别（若跨类，选主导类别并在描述中提及次要类别）：

| 类别码 | 含义 | 典型例子 |
|---|---|---|
| SEC | 安全 | 注入、越权、硬编码密钥、不安全反序列化 |
| COR | 正确性 | 逻辑错误、边界未处理、类型 / 精度错误 |
| ERR | 错误处理 | 异常吞没、失败未回滚、错误未上报 |
| CON | 并发 | 竞态、死锁、事务边界、异步顺序假设 |
| PERF | 性能 | N+1、无界增长、循环内 IO、缺少索引 |
| COMP | 兼容性 | 接口 / 数据结构破坏性变更、向后不兼容 |
| MAIN | 可维护性 | 重复、超长函数、死代码、命名混乱 |
| TEST | 测试缺口 | 核心逻辑无测试、用例未随变更更新 |
| DEP | 依赖 | 已知漏洞、过时、许可证风险 |
| CFG | 配置 / 构建 | 环境差异、缺失配置、构建脚本问题 |

问题编号格式：`<类别码>-<序号>`，如 `SEC-01`、`COR-03`。全报告内唯一。

## 2. 证据要求

每个问题必须包含（缺任一项则该问题不得定级，只能进"待确认"）：

- **位置**：`相对路径:行号`（范围用 `:起-止`）。
- **证据**：关键代码片段，或命令及其输出。
- **条件**：在什么输入 / 状态下会触发。
- **影响**：触发后的具体后果（崩溃、数据错误、越权、性能劣化等）。
- **建议**：可执行的修复方向（不必给完整补丁，但要指到改哪里、怎么改）。

区分三类陈述：
- **事实**：可由证据直接确认。
- **推断**：标"（推测）"并写明依据。
- **待确认**：缺证据，列入"未覆盖 / 不确定"。

## 3. 风险评级

用四级制，评级依据"影响 × 触发可能性 × 影响面"：

| 等级 | 名称 | 判定标准 |
|---|---|---|
| P0 | 严重 | 安全漏洞、数据丢失 / 损坏、核心流程崩溃；或影响面极大且必现 |
| P1 | 高 | 功能性缺陷、明确的回归风险、兼容性破坏；或落在高扇入 / 核心调用链 |
| P2 | 中 | 边界 / 异常处理缺陷、明显性能问题、可维护性硬伤 |
| P3 | 低 | 风格、命名、轻微重复、优化建议 |

评级必须给出一句依据（为什么是这一级）。同一问题在不同批次分析中应得到相同级别；若判级变化，需说明原因。

## 4. 测试建议格式

每条测试建议一行一表，字段固定：

| 字段 | 说明 |
|---|---|
| 编号 | `T-<序号>` |
| 目标 | 要验证的行为（一句话，具体到可断言） |
| 层级 | 单元 / 集成 / E2E |
| 输入 / 前置 | 触发条件、前置状态 |
| 预期结果 | 可断言的预期 |
| 优先级 | 对应问题风险等级 P0–P3 |
| 状态 | 已有（复用）/ 需更新 / 需新增 |
| 关联问题 | 对应问题编号，如 `COR-02` |

测试建议覆盖三来源（变更直接覆盖、影响传播覆盖、风险驱动补充），去重后按优先级排序。

## 5. 报告结构

固定按以下顺序：

1. **分析范围与假设**：项目路径、任务类型、包含 / 排除、分析深度、比较基准、默认假设。
2. **技术栈与结构结论**：栈、包管理器、目录职责分层、入口、关键模块、核心调用链。
3. **问题清单**：按风险等级从高到低排列，每条含类别码、编号、位置、证据、条件、影响、建议、等级依据。
4. **变更影响分析**（T2 / T3 含变更时）：变更摘要、影响传播、未同步改动的遗漏点。
5. **测试建议清单**：按第 4 节格式。
6. **回归范围**：为覆盖本次变更，最小需重跑的既有测试集合。
7. **未覆盖 / 不确定项**：读不到的文件、跑不了的工具、缺证据的疑点。
8. **总体结论**：一段话总结最关键的风险与建议动作。

报告可含一张汇总表（编号 / 类别 / 位置 / 等级 / 一句话描述）置于问题清单之前，便于速览。
